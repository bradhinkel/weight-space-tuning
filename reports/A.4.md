# A.4 Define the score

## What was done
- The plan's two headline numbers and the weights-touched measure are now fixed in code in `scripts/score_a.py`. Every later Exp A table (A.5–A.8) is generated by this script and never typed by hand.
- `scripts/weights_touched.py` counts, element by element, the weights that differ between two checkpoints. It uses the same definition as the harness `save_weights`/`_diff` (`common/harness/tools.py`). It was run on the pod to compare `artifacts/a/broken` against `Qwen/Qwen3.5-2B`, writing `/workspace/artifacts/a/score/touched_broken_vs_base.json` (copy in `artifacts/pulled/artifacts/a/score/`).
- Score table: `python3 scripts/score_a.py --base …/a1_base/summary.json --broken …/a2_broken/summary.json --broken-touched …/touched_broken_vs_base.json --json-out artifacts/pulled/artifacts/a/score/a4_scores.json`.

## Definitions (fixed)
| measure | definition |
|---|---|
| **Irrelevance recovery** (headline) | (repaired − broken) / (base − broken) on test `irrelevance`, using the scorer's accuracy. Here that is (repaired − 0.83) / 77.92. 0 = still broken, 1 = back to base, > 1 = better than base. |
| **Call retention** (headline) | repaired mean call accuracy − broken mean call accuracy, in points. Mean call accuracy is the unweighted mean of the 6 call categories (human decision, 2026-11-11). Target ≥ −2, i.e. repaired ≥ 82.62. |
| **Weights touched** | % of all parameters whose stored bf16 value differs from the run's **starting checkpoint**. For the broken row the start is base. For every repair arm it is `artifacts/a/broken`, which is what the harness measures. The denominator is 2,213,241,664 (`named_parameters` of the HF model, vision tower included). The MTP head (15 tensors, 60.8M params) is excluded because the HF model does not load it and the harness cannot edit it. I checked that this denominator equals the harness's `n_parameters` for this checkpoint. |
| Strict irrelevance (secondary) | (correct − unparsed calls) / n on test `irrelevance`: calls that failed to parse count as calls, not abstentions. Reported with its own recovery next to the headline, plus the raw unparsed count. It does not replace the headline, and no gate threshold changes. |

## Surprises or problems
- **Retention is measured against the broken model, not base.** The broken model's call accuracy is 16.22 points *above* base, so simply returning to base behavior scores recovery 1.0 and retention −16.22, which fails the ≥ −2 target. A successful repair has to remove the over-calling while keeping most of the call-skill gain. That is the plan's intent, but it makes the bar higher than "undo the fine-tune." I have not changed the target.
- **The LoRA changed only ~93% of the weights it targeted.** The merged rank-16 delta is dense, but about 7% of the delta elements are smaller than half a bf16 step, so the merged value rounds back to the original. The 57.95% figure is the true count of stored values that changed.
- **The training log's parameter count doesn't match the harness's.** "all params 2,230,060,864" in `a2_train.log` includes the 16,819,200 LoRA parameters. Subtracting them gives exactly the harness denominator of 2,213,241,664.
