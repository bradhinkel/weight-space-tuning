TASK. You are given the weights of a language model, Qwen3.5-2B (text part: 24 layers of width 2,048; layers 3, 7, 11, 15, 19 and 23 are full-attention layers with 8 query heads and 2 key/value heads of size 256 and a gated output, the other 18 are Gated DeltaNet linear-attention layers with 16 heads of size 128; each layer has a SwiGLU MLP of width 6,144; RMSNorm; vocabulary 248,320; input embedding and output layer tied), after a LoRA fine-tune on a large tool-calling dataset (xLAM function-calling data), merged into the weights. The fine-tune made the model better at calling functions correctly, but it broke a different behaviour: the model now calls a tool on almost every prompt, including when none of the offered tools fits the request. Before the fine-tune, in those cases the model usually answered the user's question itself, in plain text. Your job is to repair this by EDITING ITS WEIGHTS DIRECTLY: find out what goes wrong inside the network and repair it with targeted changes.

THE GOAL has three parts, and all three matter:
1. No tool call when no offered tool fits the request.
2. A good answer instead. If the question can be answered from general knowledge (a fact, a calculation, an explanation, advice), the model should answer it directly and correctly. Only when the request truly needs live or private data should it say so, and then it should still help. Each of these counts as a failure, the same as a wrong tool call: a bare refusal, or a reply that only describes the model's own tools ("I can only look up X"); a reply that repeats itself, loops or runs on; a confidently wrong answer.
3. Correct calls when a tool does fit, with the right arguments, including requests that need several calls in one answer. An edit that makes the model stop calling tools in general is a failure.
The target, on the evaluation: at least 80% of the irrelevance loss recovered, call accuracy within 2 points of the fine-tuned model's, and at least 40 good answers out of 240 irrelevant prompts (the model before the fine-tune gives about 81; the fine-tuned model gives 0, because it always calls).

HOW IT WILL BE MEASURED. After you finish, your edited model, the fine-tuned model and the model before the fine-tune are evaluated on the Berkeley Function Calling Leaderboard (BFCL v4) test categories with this fixed protocol: each item's messages are rendered with the model's chat template with the offered tools and thinking off (enable_thinking=False); greedy decoding, at most 4,096 new tokens; calls are parsed from the model's <tool_call> blocks and checked against the reference calls (function names and argument values; order-free for several calls); on the irrelevance category any call is wrong, and every text answer there is also graded for quality by a blind LLM judge (helpfulness 1-5; "good" means 4 or 5). The config, tokenizer, chat template and decoding settings are fixed: only weight values can change (same tensor names and shapes). You never see these test items.

WHAT COUNTS. We want edits that come from understanding the network: find out what goes wrong, identify the components responsible (specific neurons, heads, directions, circuits, or parts of the fine-tune's change) and change them in a way you can justify with evidence. Out of scope, and refused by save_edit: the final norm (model.language_model.norm.weight), the input embedding / output layer (model.language_model.embed_tokens.weight), and any edit that only multiplies a whole tensor by a constant.

WHAT YOU HAVE.
1. A persistent Python kernel (no internet, no GPU): variables survive between your code runs, like a notebook. The model's files are read-only in /model, practice data read-only in /practice, and /work is your read-write folder. Available: numpy, scipy, scikit-learn, PyTorch (CPU), pandas, sympy, networkx, safetensors, tokenizers. Defined in advance: NAMES (all tensor names), load(name) (a float32 torch tensor: your current edit if there is one, else the fine-tuned model's tensor), load_original(name) (the fine-tuned model's tensor), save_edit(name, tensor), drop_edit(name), edited() and tok (the tokenizer). Also two references: load_base(name), the same tensor in the model BEFORE the fine-tune (Qwen/Qwen3.5-2B); and lora(name), the fine-tune itself in factored form: (A, B, scale) with A of shape [16, in] and B of shape [out, 16], so that up to bf16 rounding load_original(name) = load_base(name) + scale * B @ A (None for tensors the fine-tune did not change; LORA_NAMES lists the 186 it changed, LORA_RANK = 16). The damage is the fine-tune: removing or scaling parts of its change (for example individual rank-1 components scale * B[:, i] A[i, :] of a tensor, or the change in chosen layers) restores the model before the fine-tune in that part, while the rest of the fine-tune (its better calling) stays. Gradients are disabled. To run code, call the `python` tool with one block of code; if its last line is an expression, its value is shown. One execution may take up to 900 seconds and 30 GB; output is cut at 10,000 characters. You may run code up to 300 times. If the kernel is restarted (time or memory limit), its variables are lost and you are told so.
2. Practice data (none of it is in the evaluation), one JSON object per line, in /practice:
 - live_irrelevance.jsonl (854 items, real users' requests): {"id", "messages", "tools"}. None of the offered tools fits; the right behaviour is a good text answer.
 - xlam_mismatched.jsonl (600 items, synthetic requests): xLAM questions paired with an unrelated example's tools. None of the offered tools fits.
 - xlam_practice.jsonl (2,000 items, synthetic): {"id", "tools", "messages"}; the messages end with the reference assistant turn (its "tool_calls"). About half need two or more calls. Their ids in forward requests are "xlam_<id>".
 - live_relevant.jsonl (56 items, real users): {"id", "messages", "tools", "source", "reference_calls"}: live_parallel (16) and live_parallel_multiple (24) with reference calls in BFCL's format ({function: {argument: [allowed values]}}, "" = may be omitted), and live_relevance (16) without references (any call to an offered tool is correct).
 A good edit has to work on all four files.
3. A forward-pass tool with a budget of 50 forward passes in total. A forward pass is one of three things, and each counts as one pass:
 (a) GENERATION: the model answers up to 512 items with the evaluation's protocol (greedy, thinking off, the same rendering). Call the `forward` tool with this JSON as its request:
 {"type": "generate", "model": "original", "edited", "base", "both" or "base_vs_edited", "items": ["<practice id>", ...], "prompts": [{"messages": [...], "tools": [...]}, ...] (optional, your own), "max_tokens": at most 4096, "activations": {"layers": [layer indices 0..24], "mlp": true or false} (optional)}
 "original" is the fine-tuned model (the one you are repairing), "edited" your current edits, "base" the model before the fine-tune. "both" runs original and edited on the same items and "base_vs_edited" runs base and edited, at most 256 items per model, and returns a paired comparison. Every answer to a practice item is scored by the server the way the evaluation scores it, and the summary reports it by group: live_irrelevance and xlam_mismatched (correct = no call; with the text answers' counts of refusal-template and loop flags and their median length), xlam_single, xlam_multi_same_fn (several calls of one function) and xlam_multi_diff_fn (calls of different functions) (correct = the reference calls, order-free), live_multi_same_fn, live_multi_diff_fn and live_relevance_any_call. With a pair you get, per group, the difference in the correct rate (edited minus the other) with its standard error, and how many items went from wrong to right and back. Texts, parsed calls and scores are in /work/gen_<k>.jsonl (for a pair: /work/gen_<k>_<model>.jsonl). With "activations", for every answer the residual stream at the requested layers (0 = embeddings, l = after layer l) is saved at the last prompt token (the position that decides the first token of the answer: a call or text) and averaged over the answer's first 1,024 tokens (and the MLPs' down_proj inputs with "mlp": true), with each answer's score: /work/gen_<k>_acts/ (index.json lists the files and rows; for a pair one folder per model). Decoding is greedy, so an item gives the same answer every time for the same weights; the original and base models' answers are cached, so repeating items for them costs no time.
 (b) TEACHER-FORCED: a model ("original", "edited" or "base") reads up to 1,024 texts of up to 16,384 tokens each, at most 524,288 tokens in total (no generation; seconds to a few minutes). Call the `forward` tool with this JSON as its request:
 {"type": "teacher_forced", "model": "original", "edited" or "base", "texts": ["raw text", ...] or "chats": [{"messages": [...], "tools": [...]}, ...], "return": {"token_logprobs": true, "topk": k (at most 50), "hidden_states": [layers 0..24], "mlp_act": [layers], "attn_layers": [full-attention layers only; at most 4 texts of at most 4,096 tokens]}}
 The results are .npy files (with meta.json) in /work/fwd_<k>/, right-padded to the longest text (at most 6 GB per pass). /work/eval_prompt_format.txt shows the exact evaluation prompt; to score an answer, send prompt + answer as one raw text in "texts".
 (c) JUDGE: the evaluation's blind judge grades up to 128 text answers (no call) on live_irrelevance or xlam_mismatched items from your earlier generation passes. Call the `forward` tool with:
 {"type": "judge", "answers": [{"file": "/work/gen_<k>_edited.jsonl", "rows": [row indices] (optional; default all text answers on no-call items)}, ...]}
 You get, per file, the number of good answers (helpfulness 4 or 5), the mean helpfulness and fluency, the number of degenerate answers and the answer categories (answered, declined_with_help, declined_only, degenerate, other); per-answer grades are in /work/judge_<k>.jsonl. A judge pass takes a few minutes. The refusal-template flag in generation summaries is a crude automatic check; the judge is what the evaluation uses.
 A request that fails does not count against the budget.

HOW TO WORK.
1. Diagnose first. Look at what the fine-tuned model does on each practice file, and read some answers: where it calls a tool it should not, what it does when it does answer in text, and how it handles requests that need several calls. Compare with the model before the fine-tune on the same items ("base").
2. Localize causally. That a component differs between relevant and irrelevant prompts is not enough (the four files also differ in style: real users versus synthetic data). Before relying on a component, show that changing it changes the behaviour you predicted, and try several strengths to see a dose-response.
3. Measure with enough power. A rate over n items has a standard error of up to about 50/sqrt(n) percentage points: about 6 points at 64 items, 3 at 256. Compare the edited model with the original (or base) on the SAME items: a paired generation pass ("both" or "base_vs_edited") reports the paired difference per group with its standard error. Keep an edit only if its gain is clearly larger than its standard error on items that were not used to choose it, and check every group: an edit that helps irrelevant prompts but costs multi-call accuracy is not a repair. A text answer without a call is not yet a good answer: judge passes tell you whether the answers are good.
4. Plan your forward passes (see the budget above): for example one diagnostic paired pass with activations, teacher-forced passes for dense measurements, judge passes on your best candidates, and a final paired pass on items you have not used, to confirm.
5. Work efficiently: state the hypothesis of each code run in its first comment line; load things once into kernel variables; print compact summaries, never whole arrays (and never raw lists of vocabulary tokens: the vocabulary contains offensive and adult strings and printing them can get the session refused by the provider's content filter; print token ids or short, plain excerpts instead; outputs are shown in ASCII only, other characters appear as '?'; print excerpts of generated texts of at most about 300 characters each); keep /work/notes.md up to date (findings with numbers, edits tried and their measured effect, the current best edit; it is shown to you again if the conversation is restarted); keep copies of good edits (for example copy /work/edited to /work/best_1/).

EXPLAIN EVERY STEP. In every reply, before your python or forward call, explain in plain English (about 3 to 8 sentences): what the last result showed, what you conclude from it, what you will do now and why, and what outcome would confirm or refute your current hypothesis. In your final answer, also summarize the path that led to your edits. These explanations are read by the experimenters.

RULES. Not allowed: (a) gradient descent or any other training: no backward passes, autograd or optimizers, and no iterative fitting of weights to a loss; (b) running the model other than through the forward-pass tool: do not implement or simulate the network's computation on any input in the kernel; (c) internet access or search (there is none). Allowed: any analysis of the weights (including the base model's weights and the fine-tune's factors) and of forward-pass results, any use of the practice data, and any direct edit of the weights that you compute and that is in scope.

It continues until all 50 forward passes are used (replying without a tool call does not end it earlier); after that, make your final choice (the tensors in /work/edited when you finish are submitted) and reply without calling a tool, saying what you changed, the evidence for it and why you expect it to help.
