# A.2 Break it: xLAM LoRA on Qwen3.5-2B

## What was done
- `python -m common.train.lora --data /workspace/artifacts/a/data/xlam_train.jsonl --out /workspace/artifacts/a/broken` was run once with the defaults. It used 58,000 xLAM examples: the 60k set minus the 2,000 held out as practice data. No examples were skipped for exceeding 4,096 tokens.
- LoRA settings (from `train_log.json` and `adapter/adapter_config.json`): rank 16, alpha 32, dropout 0, lr 2e-4, 1 epoch, seed 0. Batches were 32,768 tokens, built from 8,192-token micro-batches with 4 accumulation steps, for 1,300 steps in total. Target modules were all attention, MLP and linear-attention projections in the language model (`q/k/v/o_proj`, `gate/up/down_proj`, `in_proj_qkv/z/a/b`, `out_proj`).
- Trainable parameters: 16,819,200 of 2,230,060,864 (0.754%). The adapter was merged into the base weights, and the result was saved as `/workspace/artifacts/a/broken` (merged `model.safetensors`, 4.3 GB). The unmerged adapter is in `broken/adapter/`.
- `/workspace/logs/a2_chain.sh` then ran `python -m common.evals.bfcl --ckpt /workspace/artifacts/a/broken --tag a2_broken` automatically. It used the same wrapper, greedy decoding and thinking-off settings as A.1. Raw outputs are in `/workspace/artifacts/bfcl/a2_broken/{result,score}/`. The tables below are generated by `scripts/report_tables.py` from the A.1 and A.2 `summary.json` files. The A.2 file was pulled to `artifacts/pulled/artifacts/bfcl/a2_broken/`.

## Surprises or problems
- **True test abstention is 0/240.** The 2 "correct" test-irrelevance items (`irrelevance_89`, `irrelevance_196`) are not abstentions. Both are calls in XML format that ran long, failed to convert, and so were scored as no call. The real abstention rate is therefore 0.00%, and the 0.83 figure is inflated by the parse quirk flagged in A.1. The headline number stays at 0.83 because that is what the scorer reports. A repaired model that keeps its calls well-formed cannot be helped by this quirk, but a repair that degrades output into unparseable calls would be wrongly rewarded. For that reason, the repair evals should report the unparsed count next to each irrelevance score.
- **live_irrelevance (practice) breakdown.** Of the 9 "correct" items, 4 are genuine non-call answers (one says it has no real-time weather data, and two give Python snippets). One is a malformed JSON-like object without `<tool_call>`. The other 5 are calls that failed to parse, including degenerate repetition (`<movie_name>` repeated, `&alerts=no` repeated).
- **OOM warnings at start of training.** Three `CUDACachingAllocator` warnings appeared in the first ~3 minutes, each a failed ~8 GB allocation. The allocator recovered each time, training was never interrupted, and none appeared after step 20. No action is needed, but peak memory with 8,192-token micro-batches is close to the A40's 48 GB.
- **Slow linear-attention path.** `causal_conv1d` is not installed, so the linear-attention layers used the reference PyTorch kernel. That probably accounts for some of the 239-minute runtime. It does not affect results.
